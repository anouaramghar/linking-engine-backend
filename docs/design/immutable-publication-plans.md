# Immutable publication plans

**Guarantee:** LinkMesh publishes only the exact article change a named operator
saw and approved. No model call, placement choice, target expansion, fallback
choice, or HTML rendering happens after final approval.

## The problem this replaces

A suggestion whose status is `approved` says an editor wants a link. It says
nothing about the edit that link produces. Until this change, everything that
turned that intention into bytes happened inside the publication worker, after
the last human had left:

- the cohort and its ordering were recomputed when the worker started, so rows
  selected after a preview joined the run silently;
- missing placements were generated by a model call at publication time, so an
  editor who had been shown an appended block could get an in-text link instead;
- the connector re-ran `preview_links` during the write, so the HTML was rendered
  a second time, from inputs that could have changed;
- `POST /publish/{site_id}` published everything selected for a site, and both
  the Sites page and a fleet-wide button on the queue could call it.

The operator approved an intention. The system invented the change.

## The model

One `PublicationPlan` per source article. Publication already writes one
WordPress post per source-article group, so making that same edit the approval
unit keeps retries, staleness, audit history, and partial failures independent
and understandable.

A plan stores the whole artifact: site and source identity, the source URL,
the exact editable `original_html` read from the live post, the exact
`updated_html` that may be sent, and an ordered `items` list holding each link's
suggestion id, target URL, anchor text, and outcome.

`plan_hash` is SHA-256 over the canonical serialization of that artifact, with
`schema_version` inside the hash rather than beside it. The serialization is
`json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False)`,
UTF-8 encoded, so the digest depends on the values alone. `items` is hashed
exactly as stored, list order included — normalizing it would let a reordering
or an extra key pass unnoticed, which is precisely the tampering this catches.

Artifact fields are never updated in place. A different edit is a new row with a
new hash and needs a new approval. A PostgreSQL partial unique index on
`source_article_id` for statuses `prepared` and `approved` keeps at most one live
snapshot per post; terminal rows accumulate as history.

## The three steps

```text
POST /publish/{id}/plans/prepare   read live posts, render, store, show
POST /publish/{id}/plans/approve   a named human binds themselves to hashes
POST /publish/{id}                 queue named approved artifacts, nothing else
```

**Preparation** is where every decision now happens: reciprocal suppression,
anchor arbitration, ordering, the last placement generation, one WordPress GET
per source article, and the rendering. It is allowed to spend money and to read
the managed site. It writes nothing back to WordPress, approves nothing, and
changes no suggestion's review status. An unreachable source yields an error and
no plan, so a dead post cannot ride along in someone else's approval.

Re-preparing an unchanged article returns the same plan, so a page reload does
not invalidate an approval in progress. A changed article supersedes the previous
*prepared* plan. An *approved* plan is never superseded — that source waits until
its plan reaches a terminal state.

**Approval** depends on both site authorization and `require_operator_identity`,
so a shared service key cannot make it. In one transaction it locks every named
plan, requires the exact site, status, and hash, recomputes integrity, requires
every snapshotted suggestion to still be selected and unattached, then sets
`approved_hash`, `approved_by`, `approved_at` and links the suggestions. Any
mismatch returns 409 and approves none: approving "the ones that still match" is
approving a set nobody read.

**Queueing** makes no decision. The approval screen sends `plan_ids` for exactly
the plans it displayed; an omitted body intentionally queues every approved plan
as the recovery action. With no matching approved plan it returns 409 rather than
starting an empty job, which makes retry safe without asking for approval again.

## The worker

`publish_approved_plans` selects `PublicationPlan.status == "approved"` and never
a fresh cohort from `Suggestion.status == "approved"`. Per plan it takes the
per-source-article advisory lock, locks the plan and its suggestions with
`populate_existing` (the session does not expire on commit, so without it the row
lock would hand back attributes loaded before the lock), recomputes the hash and
compares it with `approved_hash`, then calls one connector method:

```python
apply_planned_edit(source, *, original_html: str, updated_html: str) -> str
```

It receives two strings and nothing else — no suggestion, no target, no anchor —
so there is nothing it could re-decide. Given the live content:

| live content | action |
|---|---|
| equals `original_html` | POST `updated_html` verbatim → `"written"` |
| equals `updated_html` | no POST → `"already_applied"` |
| anything else | no POST → `StalePlanError` |

An empty or no-op plan (`updated_html == original_html`) makes no request at all.

Outcomes:

- **written / already_applied** → plan and suggestions applied; each stored item
  outcome is copied to its suggestion, so "how often did a link land in the
  prose" stays answerable. `already_applied` is how a crash between the POST and
  the database commit finishes correctly on retry, without a second write.
- **stale** → no write, no RQ retry (a retry would only re-read the same changed
  article), a bounded reason on the plan, suggestion links cleared, the
  suggestions left selected, and a durable operator alert.
- **integrity mismatch** → no network access at all, plan and suggestions failed,
  links retained for audit, durable alert, non-retryable. Explicit reselection is
  the recovery path.
- **transient connector error** → rolled back, plan stays approved, RQ retries. A
  plan whose suggestions exhaust `publish_max_suggestion_attempts` becomes failed
  rather than being retried by every future run.

## What the dashboard says

The persisted suggestion enum value `approved` is unchanged — a database enum
rename would add migration risk without strengthening anything — but operator
copy calls it **Selected**. The queue chip reads "Selected", bulk success reads
"selected for preparation", and nothing on the queue promises publication.

The modal renders each plan's exact current and after HTML, its links and
outcomes, and its hash-derived identity, and its button reads **Approve and queue
N exact edits**. It sends exactly the visible `{id, plan_hash}` pairs; `has_more`
and per-source errors describe work explicitly *not* in the request. Approval and
queueing are two sequential mutations, and that queue call names the same visible
plan IDs. An approval that succeeds while queueing fails shows as **approved, not
queued** with a queue-only retry.

The fleet-wide publish button and the Sites page's "Publish approved" action are
gone. The Sites page now links to `/queue?site=<id>&status=approved`, labelled
"Review publication changes".

## Residual limitation

**WordPress core exposes no compare-and-swap precondition on post updates.** The
connector re-reads the post immediately before the write and refuses if it is
neither snapshot, which narrows the race between that read and the POST — it
cannot close it. An editor who saves the post inside that window has their change
overwritten by the approved content.

This is an application-level guarantee: LinkMesh intentionally sends only the
approved HTML and refuses known drift. Closing the residual race would need a
WordPress compare-and-swap plugin, which is deliberately out of scope here.

## Deployment

This is a coordinated contract change. Use a short maintenance window.

1. Stop/drain publication workers, so old code cannot publish selected rows
   during the rollout.
2. Back up the database.
3. Apply the Alembic migration (`a1c7e93f6b25`). Existing selected suggestions
   are deliberately **not** backfilled into approved plans — nobody has seen the
   edits they produce. They migrate with `publication_plan_id = NULL`, stay
   selected, and need preparation plus explicit approval.
4. Deploy the API and the publication worker together.
5. Deploy the frontend immediately afterwards.
6. Verify `POST /publish/{site_id}` returns 409 for a site with selected
   suggestions and no approved plan.
7. Restart the publication workers.

**Rollback rule:** rolling back application code after the migration is unsafe,
because old workers ignore plans and publish directly from selected suggestions.
If rollback is required, keep publication workers stopped until both code and
schema are restored, or deploy a forward fix.
