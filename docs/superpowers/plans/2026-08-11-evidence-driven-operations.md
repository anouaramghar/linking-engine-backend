## Goal

Make publication, sensitive administration, editorial review, evaluation, model decisions, and workflow improvement demonstrably safer and more useful.

Every implementation decision in this plan follows one rule:

> Every decision must prove a useful improvement over the current baseline, with evidence proportional to its cost and risk.

For each workstream, record:

1. the problem and current baseline;
2. the expected improvement;
3. the measurement and evidence source;
4. the cost and risk;
5. the acceptance threshold;
6. the stop, rollback, or reconsideration condition.

## Scope

This plan covers:

1. safe WordPress publication: fail closed on unsupported editors and verify after publication;
2. named-human attribution for sensitive administration;
3. reason-coded editorial evidence;
4. a versioned Evaluation workspace backed by real evidence;
5. a frozen three-site baseline before model changes;
6. measurement of the current review/publication workflow.

The two controls in Workstream 1 share the same publication boundary but have separate evidence gates. Workstreams 4, 5, and 6 share evidence contracts but have separate deliverables and acceptance decisions.

This plan does **not** cover:

- autonomous agents, chat-driven execution, or Telegram workflow expansion;
- user roles or per-person authorization scopes;
- a general analytics platform;
- a new job queue or scheduler;
- automatic publication rollback or republishing;
- changing the embedding model, reranker, chunk size, or retrieval method;
- production publication during implementation tests.

## Chosen architecture

Keep the design deliberately small:

- one pure WordPress editor classifier at the connector boundary;
- one publication-verification service, invoked after a successful write;
- two append-only evidence tables: administrative audit events and suggestion review events;
- one versioned evaluation JSON contract generated by the existing evaluation scripts;
- one protected read endpoint for the Evaluation page;
- no analytics SDK, chart dependency, scheduler, new worker kind, or agent framework.

The principal data flow is:

```text
prepare publication
  -> classify source editor
  -> unsupported: fail closed with a reason code
  -> supported: create immutable plan
  -> named human approves exact {plan_id, plan_hash}
  -> publication worker writes the planned HTML
  -> plan becomes applied + verification pending
  -> verifier reads WordPress without writing
  -> verified_exact | verified_links | mismatch | unavailable

human review decision
  -> append review event with actor, source, reason, and duration
  -> evaluation artifact and live aggregates
  -> Evaluation page shows provenance and sample sufficiency
  -> three-site gate decides whether a future model proposal is justified
```

## Workstream 1: Safe WordPress publication

This workstream is complete only when both controls below pass. Failing closed prevents unsafe writes; post-publication verification detects an incorrect or altered result after a supported write.

### Part A: Verify after publication

#### Decision record

- **Problem:** a successful WordPress write currently proves that the API accepted a request, not that the intended links remain present when the document is read back.
- **Current baseline:** applied publication plans and write failures are stored, but there is no durable verification result.
- **Expected improvement:** every newly applied plan has a visible, durable read-after-write outcome, and mismatches are surfaced without causing a second mutation.
- **Measurement:** verified plans / applied plans, mismatches, unavailable checks, verification attempts, and time from `applied_at` to `verified_at`.
- **Initial acceptance threshold:** 100% of newly applied plans enter a terminal verification state or a visible retryable `unavailable` state; no verification path performs a WordPress write.
- **Stop/rollback:** disable verifier invocation if it causes publication failures or performs mutations. Preserve the additive database fields and continue recording `pending` until the read path is repaired.

#### Backend data contract

Add an additive migration and fields to `app/models/publication_plan.py`:

```text
verification_status: nullable string/enum
  pending
  verified_exact
  verified_links
  mismatch
  unavailable
verification_attempts: non-null integer, default 0
verified_at: nullable timestamp
verification_error: nullable bounded text
verified_html_hash: nullable SHA-256 hex string
```

Rules:

- old unapplied and applied rows may remain `NULL`; the migration must not invent historical evidence;
- a newly successful write sets `verification_status = pending` in the same transaction that records `applied_at`;
- `verification_error` contains a sanitized bounded summary, never response bodies or credentials;
- expose the fields through `PublicationPlanOut` in `app/schemas/publication.py`.

#### Verification module

Create `app/services/publication_verification.py` with one narrow public interface:

```python
def verify_plan(db: Session, plan_id: int) -> VerificationResult:
    """Read the current WordPress document, classify the result, and persist it."""
```

Keep connector-specific fetching, HTML hashing, intended-link comparison, result classification, and persistence behind this interface.

Classification rules:

1. `verified_exact`: normalized read-back HTML equals the exact HTML written by the plan.
2. `verified_links`: WordPress normalized the document, but every planned `(href, anchor)` occurrence is present exactly as intended and no planned occurrence is duplicated.
3. `mismatch`: a planned link is missing, points elsewhere, has the wrong anchor, or appears more times than planned.
4. `unavailable`: authentication, networking, timeout, or a transient/non-comparable read prevents verification.

On every attempt:

- increment `verification_attempts`;
- set `verified_at` only for `verified_exact` or `verified_links`;
- store a hash of the read-back HTML when content was obtained;
- preserve enough bounded diagnostics to explain a mismatch without storing the whole document;
- never call the WordPress write endpoint;
- never republish, roll back, or supersede the plan automatically.

#### Worker integration

Integrate into the existing publication worker in two transactions:

1. commit the successful publication result and `verification_status = pending`;
2. call `verify_plan` as a read-only follow-up and commit its result.

If verification raises unexpectedly, the publication remains `applied`; record `unavailable` in a recovery transaction. A verification error must not turn an already successful publication into a publication failure.

Do not add a new RQ queue or scheduled sweep initially. Add a protected manual retry route:

```http
POST /api/v1/publication/plans/{plan_id}/verify
```

Requirements:

- require tenant/site access and `require_operator_identity`;
- only accept applied plans;
- return the updated `PublicationPlanOut`;
- be idempotent and safe to repeat;
- reject plans with no readable WordPress source using a clear 4xx response.

#### Frontend integration

Integrate with the current publication UI, particularly the current versions of:

- `src/pages/PublishPage.tsx`
- `src/components/publish/PublicationReview.tsx`
- the publication API client/hooks

Display one of:

- Verification pending
- Verified exactly
- Verified: WordPress normalized formatting
- Verification mismatch — manual inspection required
- Verification unavailable — Retry verification

Only show the retry action for `unavailable` and `mismatch`. The button calls the manual verification endpoint; its label must not imply republishing.

#### Tests

Backend unit/integration tests must cover:

- exact HTML match;
- semantically intact link after harmless WordPress normalization;
- missing link, wrong target, wrong anchor, and duplicate occurrence;
- transient WordPress read failure;
- unexpected verifier exception after an applied write;
- retry route authorization, applied-plan restriction, idempotency, and tenant isolation;
- migration defaults and API serialization;
- proof that verification invokes no write method.

Frontend tests must cover every status, retry visibility, retry success/failure, and wording that distinguishes verification from republishing.

### Part B: Fail closed on unsupported WordPress editors

#### Decision record

- **Problem:** editing unknown block or page-builder syntax can create syntactically valid HTML while corrupting editor-owned structure.
- **Current baseline:** LinkMesh can preserve core Gutenberg comments, but the connector acknowledges that third-party block delimiters may be invalid after editing.
- **Expected improvement:** LinkMesh refuses to prepare or publish when it cannot prove its edit strategy is safe.
- **Measurement:** preparation failures by editor reason code, false blocks found during staging review, and zero writes for rejected documents.
- **Initial acceptance threshold:** all known third-party blocks and builder shortcodes in the test corpus fail before a plan is created; supported Classic/core-Gutenberg fixtures still prepare unchanged except for the intended link.
- **Stop/rollback:** if the classifier blocks ordinary supported content, correct its pure rules and fixtures. Never replace fail-closed behavior with a blind fallback.

#### Connector boundary

Add a pure classifier near the existing edit logic in `app/connectors/wordpress.py`:

```python
class EditorSupport(...):
    supported: bool
    editor_kind: str
    reason_code: str | None

def classify_editor_support(raw_html: str) -> EditorSupport:
    ...
```

Initial rules:

- support Classic HTML when no known builder shortcode marker is present;
- support Gutenberg documents containing only WordPress core block names;
- reject any serialized third-party/custom block name;
- reject known page-builder shortcode markers;
- reject absent/non-editable source content;
- do not infer safety from rendered HTML alone.

Use stable reason codes:

```text
third_party_block
builder_shortcode
missing_editable_content
unsupported_editor_structure
```

Do not add a general parser dependency. Use narrowly tested recognition of WordPress block comments and builder markers.

#### Enforcement point

Call the classifier at the start of `preview_links`, before `_insert_link`, before any fallback insertion, and before plan persistence.

On rejection:

- raise a specific `UnsupportedEditorError` carrying the reason code;
- return a per-source preparation error to the caller;
- create no publication plan;
- perform no WordPress write;
- do not append the link at the end of the document;
- expose a clear UI message: “This editor is not supported safely yet. No changes were made.”

The publication path must also recheck support when it reads the current edit-context document for drift. This protects older prepared plans if the editor structure changes before approval.

#### Tests and fixtures

Add fixtures for:

- Classic HTML;
- core Gutenberg paragraph/heading/list blocks;
- nested core blocks;
- a custom `namespace/block` Gutenberg block;
- Elementor, Divi, WPBakery, and generic shortcode-shaped builder content;
- missing edit-context source;
- mixed core and custom blocks.

Tests must assert classification, reason code, no plan persistence, no write call, and unchanged supported output outside the intended edit.

## Workstream 2: Require a named human for sensitive administration

### Decision record

- **Problem:** network restrictions and API keys restrict access, but they do not identify which approved person changed credentials or deleted resources.
- **Current baseline:** named operator identity is required for publication approval and pool governance, but not consistently for WordPress credentials, site deletion, or tenant/key administration.
- **Expected improvement:** sensitive changes are attributable to an approved person without introducing roles or changing the full-access membership model.
- **Measurement:** percentage of sensitive mutations with a durable actor and audit event; target 100% after deployment.
- **Initial acceptance threshold:** an anonymous/shared-key-only request cannot execute a listed sensitive action; every successful action creates one sanitized append-only event.
- **Stop/rollback:** if a legitimate surface cannot provide operator identity, keep that mutation disabled until its authentication handoff is fixed. Do not silently fall back to a shared system identity.

### Audit model

Create `AdministrativeAuditEvent` in a new model and migration with:

```text
id
tenant_id
actor_identity
action
site_id nullable, without destructive cascade
site_name_snapshot nullable
target_type
target_id nullable
metadata_json sanitized and bounded
created_at
```

The event must survive site deletion. Add a small service/helper:

```python
record_admin_action(db, *, actor, action, target, metadata=None)
```

Do not build a generic event bus. The helper validates the allow-listed metadata keys and prevents secret-shaped values.

### Protected actions

Require `require_operator_identity` and append an event for:

- set/replace WordPress credentials;
- clear WordPress credentials;
- delete a site;
- create, rotate, revoke, or delete tenant/API keys;
- create/delete a tenant;
- create or bulk-import a site when credentials are included.

Preserve Amir’s current access decision:

- approved members retain the same full application access;
- no per-person roles are introduced;
- firewall/IP restrictions remain the network boundary;
- Telegram/dashboard approval remains the human admission layer;
- the change adds attribution and auditability, not authorization tiers.

### Transaction behavior

- Record the audit event in the same database transaction as the sensitive mutation where possible.
- For site deletion, capture the site name and identifiers before deletion.
- If audit insertion fails, fail the sensitive mutation closed.
- Return no audit metadata containing credentials, credential presence beyond a boolean, raw keys, or request headers.

### Read surface

Add a protected, tenant-scoped read endpoint with bounded pagination:

```http
GET /api/v1/admin/audit-events?limit=...&before=...
```

An initial backend endpoint is sufficient. Do not build a large frontend audit explorer in this workstream. If a small existing Administration page can accept a recent-events table without disturbing current WIP, show actor, action, target snapshot, and time only.

### Tests

Cover each protected action for missing identity, successful named identity, tenant isolation, exact single-event creation, secret redaction, transaction rollback, and site-event survival after deletion.

## Workstream 3: Capture reason-coded human review evidence

### Decision record

- **Problem:** approved/rejected state alone is too weak to diagnose retrieval quality, train/evaluate future ML changes, or distinguish individual judgement from rule-driven bulk actions.
- **Current baseline:** suggestions retain current status and `reviewed_at`, but not a durable actor, reason, source, correction history, or decision duration.
- **Expected improvement:** individual editorial decisions become usable labelled evidence, while bulk automation remains explicitly separate.
- **Measurement:** individual labelled decisions, reason distribution, correction/undo rate, median decision duration, and label coverage by site/rank/method.
- **Initial acceptance threshold:** 100% of new individual approve/reject mutations append a named event with a valid reason; bulk actions are labelled as bulk and excluded from human-quality ground truth.
- **Stop/rollback:** if the reason prompt materially slows review without improving diagnosis, reduce the fixed list after measuring duration and correction rate; do not remove event provenance.

### Review event model

Create an append-only `SuggestionReviewEvent` table and migration:

```text
id
suggestion_id
site_id
tenant_id
operator_identity
new_status
reason_code
source: individual | bulk_ids | bulk_filter
decision_duration_ms nullable
created_at
```

Keep the current suggestion status as the operational projection. The event history is evidence and must not be rewritten when an operator undoes or changes a decision.

### Reason contract

Use a fixed API enum; do not accept arbitrary free text initially.

Individual approval:

```text
relevant_target
```

Individual rejection:

```text
weak_relevance
wrong_target
duplicate_or_redundant
already_linked
unsafe_or_inappropriate
```

Correction:

```text
undo
```

Server-assigned bulk reasons:

```text
bulk_manual_selection
bulk_threshold_rule
```

### API integration

Extend the existing `SuggestionReview`, `BulkReview`, and `BulkReviewFilter` contracts without duplicating route logic.

- Require `require_operator_identity` for review mutations that create editorial labels.
- Individual approve/reject requires an allowed reason code.
- Bulk-by-ID uses source `bulk_ids` and server reason `bulk_manual_selection`.
- Bulk-by-filter uses source `bulk_filter` and server reason `bulk_threshold_rule`.
- Undo appends a new individual `undo` event and updates the operational suggestion state.
- Update the suggestion and append the event in one transaction.
- Reject negative or unreasonable durations; cap accepted duration at 30 minutes.

Only the latest valid `individual` decision per suggestion is eligible as human-labelled evaluation ground truth. Bulk events remain operational evidence but are not human labels.

### Frontend integration

Integrate into the current `ValidationPage.tsx` and its current component structure without replacing the user’s ongoing selection/publish work.

- Show the compact reason choice only for individual decisions.
- Default approval to `relevant_target` so approval remains one clear action.
- Require a rejection reason before submitting.
- Measure duration with `performance.now()` from when a suggestion’s review detail becomes actionable until submission.
- Send a bounded integer `decision_duration_ms`; never use it for employee scoring.
- Bulk actions require no per-item dialog and use the server-assigned bulk reason.
- Undo must remain available and produce an explicit correction event.

### Tests

Backend tests cover reason/status compatibility, actor requirement, individual vs bulk provenance, event append behavior, undo history, transaction atomicity, duration bounds, tenant isolation, and ground-truth selection.

Frontend tests cover approval default, mandatory rejection reason, duration submission, bulk behavior, undo, errors, and keyboard/accessibility behavior.

## Workstream 4: Connect Evaluation to versioned evidence

### Decision record

- **Problem:** the Evaluation page currently communicates intent but is not connected to a trustworthy, reproducible evidence source.
- **Current baseline:** evaluation scripts emit metric summaries, and a JSON result exists, but it lacks a complete provenance envelope; the UI reports that the pipeline is not connected.
- **Expected improvement:** operators can see what was measured, on which sites and labels, with which code/method/cutoff, and whether the sample is sufficient.
- **Measurement:** artifact validation, UI/API contract tests, freshness/provenance visibility, and zero metrics displayed without sample counts.
- **Initial acceptance threshold:** every displayed metric is traceable to a schema version, generation time, code revision, ground-truth type, site set, cutoff, method, `k`, and sample count.
- **Stop/rollback:** if the artifact is missing, invalid, stale, or insufficient, render an explicit unavailable/insufficient state; never fall back to invented, cached-without-provenance, or score-as-confidence data.

### Versioned artifact

Update `scripts/run_evaluation.py` to write a versioned envelope instead of a bare site dictionary:

```json
{
  "schema_version": 1,
  "generated_at": "ISO-8601 UTC",
  "git_commit": "commit or null",
  "cutoff": "ISO-8601 UTC or null",
  "ground_truth": "editor_individual | observed_proxy",
  "k": 5,
  "method": "hybrid | semantic | lexical | comparison",
  "site_ids": [1, 2, 3],
  "sample_counts": {
    "labelled_suggestions": 0,
    "eligible_queries": 0,
    "sites": 3
  },
  "summaries": {
    "1": {},
    "2": {},
    "3": {},
    "all": {}
  }
}
```

Exact metric fields remain owned by the existing evaluation script. Add Pydantic validation in the backend and tests for schema and semantic constraints.

Store the generated, reviewed artifact at:

```text
app/data/evaluation-baseline.json
```

This is a packaged read-only artifact, not a database table. Regeneration is an explicit engineering operation. Do not allow the dashboard to write or mutate it.

If `ground_truth = observed_proxy`, label it prominently as proxy evidence and do not use it alone to approve a model change.

### Backend read endpoint

Add:

```http
GET /api/v1/evaluation/summary
```

The protected endpoint returns:

- validated artifact provenance and offline summaries;
- live editorial aggregates derived from `SuggestionReviewEvent`;
- live publication aggregates derived from publication-plan timestamps and verification status;
- a computed `sample_state`: `sufficient`, `insufficient`, `missing`, or `stale`;
- a list of human-readable limitations.

Keep calculations in `app/services/evaluation_summary.py`, not in the route. Query aggregates in SQL; do not load all event rows into Python. Bound any per-site breakdown.

Recommended initial sufficiency rule for model-decision use:

```text
at least 100 latest individual labelled decisions per selected site
and at least 3 selected sites
```

This is a starting evidence gate, not a claim of universal statistical significance. Return counts so it can be reconsidered transparently.

Define artifact staleness as a configurable/documented age, initially 30 days, or a code revision mismatch when a strict comparison run is requested. Staleness must be visible, not silently hidden.

### Frontend Evaluation page

Replace the disconnected placeholder in `src/pages/EvaluationPage.tsx` with a real API client/hook and native cards/tables. Do not add a chart library.

Display:

- evidence status and limitations first;
- ground-truth type and whether it is human or proxy;
- generated time, code revision, cutoff, method, and `k`;
- sample counts overall and per site;
- existing offline ranking metrics such as NDCG@5, Recall/Hit@5, and MRR@5 when supplied;
- individual human acceptance and rejection reasons by rank/method;
- publication verification and failure rates;
- workflow timing aggregates from Workstream 6.

Never call cosine similarity “confidence,” “accuracy,” or “quality.” It is a ranking score. Never show a percentage without its numerator/denominator or sample count.

Explicit empty states:

- Evidence unavailable
- Evidence is stale
- Proxy evidence only
- More individual labels required: `current / target`
- Three-site baseline ready

### Tests

Cover artifact schema validation, missing/corrupt/stale files, SQL aggregate correctness, tenant/site isolation, sample-state boundaries, observed-proxy labels, endpoint authorization, frontend empty/loading/error/sufficient states, and provenance rendering.

## Workstream 5: Establish a three-site baseline before model changes

### Decision record

- **Problem:** model changes cannot prove improvement without a frozen representative baseline.
- **Current baseline:** LinkMesh has evaluation scripts and recorded experiments, but no agreed three-site gate tying a future default change to the same sites, labels, cutoff, and provenance.
- **Expected improvement:** future proposals can be accepted or rejected against reproducible evidence rather than intuition.
- **Measurement:** a versioned baseline plus repeatable comparison runs using identical sites, labels, cutoff, `k`, and code metadata.
- **Initial acceptance threshold:** three operator-selected representative sites, at least 100 latest individual labels per site, a valid versioned artifact, and complete limitations. If the label gate is not met, report `insufficient`; do not change defaults.
- **Stop/rollback:** pause model comparison when site selection, labels, or provenance are unreliable. A failed comparison means retain the current default; it does not justify tuning until a desired result appears.

### Site selection and freeze record

Do not hard-code site IDs in application code. Create a runbook at:

```text
docs/evaluation/three-site-baseline.md
```

The operator selects three WordPress sites representing materially different content shapes, for example:

- smaller editorial site;
- larger/deeper content site;
- structurally or linguistically different site.

For each run, record in the artifact or an adjacent generated manifest:

- selected site IDs and non-sensitive names;
- selection rationale;
- label cutoff;
- ground-truth source;
- `k` and candidate-generation method;
- current model and chunk configuration;
- code commit;
- sample counts and exclusions;
- run command and generation time.

### Baseline metrics

Retain the current production/default method as the baseline. Report, where meaningful:

Offline ranking:

- NDCG@5;
- Recall/Hit@5;
- MRR@5;
- eligible query and label counts.

Human review:

- individual acceptance rate overall and by final rank/method;
- rejection-reason distribution;
- correction/undo rate;
- median and p75 decision duration.

Publication/operations:

- prepared-to-approved duration;
- approved-to-applied duration;
- applied-to-verified duration;
- verified / mismatch / unavailable rates;
- failed and stale-plan rates;
- prepared plans older than 24 hours with no approval as an abandonment proxy.

Always display denominators. Do not interpret the abandonment proxy as a confirmed abandoned task without user research.

### Comparison gate for future ML changes

A future model/retrieval proposal may become the default only when all of these hold on the same frozen evidence set:

1. no material regression on any selected site’s primary ranking metrics;
2. aggregate ranking improvement is reproducible;
3. human acceptance/correction evidence does not worsen after rollout or shadow testing;
4. latency, memory, hosting cost, and operational complexity remain within an explicitly recorded budget;
5. publication verification/failure behavior does not regress;
6. the comparison artifact includes limitations and can be regenerated.

Before a live A/B or default change, write numerical thresholds for that proposal. Do not retroactively choose thresholds after seeing results.

## Workstream 6: Measure the current review and publication workflow

### Decision record

- **Problem:** workflow redesign cannot prove usefulness while review effort, corrections, waiting time, and publication outcomes are unmeasured.
- **Current baseline:** existing timestamps provide part of the operational history, but review duration/reasons/corrections and post-publication verification are missing.
- **Expected improvement:** the team can locate the largest evidenced bottleneck and test one reversible workflow change at a time.
- **Measurement:** review duration, correction rate, decision-source mix, prepared-to-approved time, approved-to-applied time, applied-to-verified time, abandonment proxy, and publication result rates.
- **Initial acceptance threshold:** every dashboard aggregate has a precise event/timestamp definition and denominator; at least one complete baseline window is recorded before proposing a redesign.
- **Stop/rollback:** if an event is ambiguous or creates surveillance risk, remove it from product decisions until its meaning is corrected. Never use operator duration for employee ranking.

### Event derivations

Do not introduce a generic analytics event table. Derive the first baseline from the durable domain evidence already added by this plan:

- review duration and corrections from `SuggestionReviewEvent`;
- prepared-to-approved from `PublicationPlan.created_at -> approved_at`;
- approved-to-applied from `approved_at -> applied_at`;
- applied-to-verified from `applied_at -> verified_at`;
- publication result rates from plan status and `verification_status`;
- prepared plans older than 24 hours with no approval as an abandonment **proxy**.

Use median and p75 for elapsed time; do not report only averages. Every rate must include its numerator, denominator, time window, and included sites. Never present the abandonment proxy as confirmed abandonment.

### Workflow-improvement gate

Measure the existing workflow before redesigning it. After enough events exist, identify the single largest evidenced bottleneck and propose one reversible change.

Examples:

- If rejection requires substantially longer than approval, improve relevance/context display and compare median duration and correction rate.
- If plans wait primarily before approval, improve the publish queue’s visibility and compare prepared-to-approved time.
- If verification is often unavailable, improve retry/recovery before adding more publication throughput.

A workflow change is accepted only when its intended metric improves without worsening correction rate, publication safety, or operator clarity. Otherwise revert the UI/behavioral change and retain the measurements. This workstream measures and defines the gate; it does not authorize a redesign in the same change set.

### Shared runbook commands

Document exact commands using the existing scripts, including an explicit output path and site IDs. The final form should resemble:

```powershell
.\.venv\Scripts\python.exe scripts\run_evaluation.py `
  --site-id <SITE_A> --site-id <SITE_B> --site-id <SITE_C> `
  --k 5 `
  --output app\data\evaluation-baseline.json
```

If the current script accepts different arguments, update it minimally and document the actual CLI. The command must fail non-zero for an invalid artifact or insufficient required inputs; insufficient label counts may still generate a valid artifact whose `sample_state` is `insufficient`.

### Tests

Cover deterministic output for fixed inputs, three-site argument validation, manifest/provenance completeness, label cutoff behavior, latest-individual-label selection, exclusion of bulk labels, aggregation denominators, median/p75 duration calculation, abandonment proxy, and comparison of identical artifacts.

## Acceptance checklist

The implementation is complete only when all are true:

- [ ] Unsupported/custom editor structures fail before plan creation and before any write.
- [ ] Supported Classic/core-Gutenberg fixtures still prepare the exact intended edit.
- [ ] Every new applied plan enters a visible verification state.
- [ ] Verification is read-only and cannot republish or roll back.
- [ ] Mismatch and unavailable states are durable, visible, and manually retryable.
- [ ] Every listed sensitive admin mutation requires a named human.
- [ ] Every successful sensitive mutation creates one sanitized durable audit event.
- [ ] Individual review labels contain actor, reason, source, time, and append-only correction history.
- [ ] Bulk actions are visibly distinct and excluded from human-labelled ground truth.
- [ ] The Evaluation endpoint rejects invalid evidence and exposes provenance and sample sufficiency.
- [ ] The Evaluation UI never presents a similarity score as confidence or a metric without its sample size.
- [ ] Three sites and their selection rationale are recorded without hard-coding them into the product.
- [ ] Insufficient evidence blocks a default model/retrieval change.
- [ ] Workflow proposals are based on measured bottlenecks and have explicit rollback criteria.
- [ ] Backend tests, Ruff, migrations, frontend tests, lint, and build pass.
- [ ] Staging WordPress validation passes without any unapproved production publication.
- [ ] Existing frontend WIP and unrelated user changes are preserved.

## Suggested review/commit boundaries

These are review boundaries only. Do not commit without authorization.

1. Backend: additive evidence models and migration.
2. Backend: editor support classifier and fail-closed preparation.
3. Backend: publication verification service and retry endpoint.
4. Backend: sensitive admin attribution and audit API.
5. Backend: review evidence events and evaluation summary contract.
6. Frontend: verification and reason-coded review integration.
7. Frontend: connected Evaluation workspace.
8. Docs/data: three-site runbook and reviewed baseline artifact.

For each boundary, the implementation handoff must state:

- files changed;
- tests run and exact result;
- baseline and expected improvement addressed;
- evidence now available and evidence still pending;
- migration/runtime impact;
- rollback path;
- whether any staging publication occurred.

## Final handoff standard

Do not say a workstream “improved” the product merely because code and tests pass. Report it as:

- **implemented and technically verified** when contracts/tests/runtime checks pass;
- **evidence collection active** when real operator or staging samples are still accumulating;
- **useful improvement proven** only when the workstream’s stated metric meets its acceptance threshold without violating its safety or cost constraints.
